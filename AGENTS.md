# AGENTS.md

Node 24 + TypeScript (ESM), no framework. Flow: `npm run fetch:emails` → `src/imap.ts` (IMAP → `emails.json`), then `npm run classify` → `src/classify.ts` (Jev + memoria → `results.json`), then `npm run dashboard` → `src/dashboard.ts` (panel local). SQLite usa el módulo nativo `node:sqlite`, por lo que `classify` y `dashboard` corren con `--experimental-sqlite` (ya incluido en los scripts npm).

## Commands
- `npm install`
- `npm run fetch:emails` — IMAP read-only, last 20 INBOX messages → `emails.json` (needs `IMAP_*` in `.env`)
- `npm run classify` — builds then classifies `emails.json`, writes `results.json` (needs `TYPESAFE_API_KEY` in `.env`)
- `npm run dashboard` — panel local en http://127.0.0.1:3000 (solo loopback); lee `results.json`/`emails.json` y escribe `data/reviews.json`
- `npm run typecheck` — `tsc --noEmit`
- `npm run ingest:new` — descubrimiento incremental por UID (solo mensajes posteriores al cursor) + recuperación de pendientes; la 1ª ejecución solo fija el punto de partida y NO clasifica el histórico
- `npm run ingest:history` — recorre el histórico por lotes (`--limit=N` o `INGEST_BATCH`, default 50); continúa en ejecuciones posteriores sin duplicar
- `dist/ingest.js <new|history> [--limit=N]` para controlar el tamaño de lote directamente
- No test framework: verify with typecheck plus real runs. `IMAP_PASSWORD=wrong …` (auth error, `emails.json` untouched) and `TYPESAFE_API_KEY=invalid …` (401 per email, batch continues) exercise error paths.

## Repo facts
- IMAP: `getMailboxLock(..., { readOnly: true })` for the whole run; only the text/plain (or HTML fallback) MIME part is downloaded, so attachments are never fetched. Bodies are capped at 10,000 chars. `emails.json` is written only after a successful retrieval; flags are re-checked afterwards.
- Jev API: `POST https://api.typesafe.ai/v1/systemone`. `src/jev.ts` envía UNA petición conjunta por correo con las preguntas del clasificador base (`category` choice, `spam` y `needsAttention` noul) más una pregunta por clasificador configurable activo. El contrato acepta varias preguntas con nombres propios y las responde con esos nombres. `jev-latest` resuelve a un modelo versionado (p. ej. `jev-1.13.0`) — reporta el nombre devuelto. `classifyEmail` conserva la firma legada (solo base) para compatibilidad.
- Env comes from `node --env-file-if-exists=.env`; never hardcode keys or log passwords/Authorization headers.
- `emails.json` and `results.json` are generated and gitignored — they contain real mailbox data. Do not commit them. `results.json` must keep the original email `id`; one failed call must not abort the batch.
- `src/jev.ts` needs no changes for IMAP; extra fields in `emails.json` (`uid`, `uidValidity`, `messageId`, `date`) are ignored by the classifier.
- Reviews are keyed by `IMAP_USER|IMAP_MAILBOX|UIDVALIDITY|UID` (account comes from env), so they survive refetch/reclassify. The dashboard serves only `/`, `/api/data`, `POST /api/reviews`, `POST /api/rules`, `POST /api/rules/toggle`, `POST /api/classifiers`, `POST /api/classifiers/update`, `POST /api/classifiers/toggle` — no static files, no filesystem paths. Cost is only shown when `JEV_INPUT_USD_PER_1M`/`JEV_OUTPUT_USD_PER_1M` are set; otherwise "tarifa no configurada".
- Memoria en `data/jev.sqlite` (gitignored, módulo nativo `node:sqlite`). Tablas `rules` (manuales, EMAIL/DOMAIN → PUBLICIDAD/MANTENER) y `classifications` (una fila por `email_id` + `criteria`). Resolución por correo: regla EMAIL > regla DOMAIN > caché del mismo mensaje > Jev. Cada decisión lleva `source` (`JEV`/`RULE`/`CACHE`); el resumen expone `jevCalls` y `avoidedCalls`.
- Las reglas NUNCA se crean automáticamente a partir de Jev; solo desde el dashboard. Dominios exactos: `x.com` no cubre `sub.x.com`. Cambiar `CRITERIA_VERSION` en `src/memory.ts` invalida la caché. Si SQLite falla, `memory.ts` degrada en silencio y se llama a Jev siempre (nunca inventa).
- Clasificadores configurables (`classifiers` en SQLite): `base` es fijo (no editable ni deshabilitable); los demás son `choice` (2-20 opciones) o `noul`, creados/editados desde el dashboard. Editar la semántica (pregunta/tipo/opciones) sube `version` y cambia `criteria` → invalida SOLO la caché de ese clasificador. Reglas y caché van por `classifier_id`; una regla de un clasificador no afecta a otro. Resolución por clasificador: regla EMAIL > regla DOMAIN > caché (mismo criteria) > Jev. La validación de estas operaciones va FUERA de `withDb` (que silencia errores y degradaría a falso éxito).
- `data/jev.sqlite` migra solo a esquema v2 (tablas `classifiers`, `rules` con `classifier_id`, `classifications` con clave compuesta). Las tablas v1 se conservan como `rules_v1_backup`/`classifications_v1_backup` (rollback manual). `results.json` añade `classifiers[]` por correo además del `classification` base legado.
- Ingesta incremental (esquema v3, aditivo): `ingest_messages` con identidad compuesta UNIQUE `(account_id, mailbox, uid_validity, uid)` y estados DISCOVERED/FETCHED/FAILED; `ingest_cursors` por época de UIDVALIDITY. `src/ingest.ts` descubre por UID (`search {uid}`), persiste ANTES de avanzar el cursor, y procesa pendientes (DISCOVERED/FAILED) por lotes — no los últimos 20. Un fallo de descarga/clasificación marca FAILED (recuperable, `attempts++`), nunca pierde el mensaje ni avanza el cursor. Cambio de UIDVALIDITY = época nueva: no reutiliza cursores ni pendientes anteriores. `classifyEmails()` (en `classify.ts`) es el motor reutilizable; `ingest.ts` lo llama y persiste en `emails.json`/`results.json` fusionando por `id` (acumulativo). `imap.ts` y `classify.ts` exportan helpers y solo ejecutan su CLI cuando se invocan directamente.
